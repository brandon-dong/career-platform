# Exercise 05: DNS/TLS failure during the Railway cutover

## 1. Setting and prediction

This is a real failure that occurred during/after the Azure VM to Railway migration. DNS is at Cloudflare (DNS only, grey cloud). I checked from my laptop on my home network, using Cloudflare's (1.1.1.1) and Google's (8.8.8.8) public resolvers.

**Failed check:** `curl https://brandondong.me/healthz` (and opening `https://brandondong.me` in Chrome).

**Prediction:** after I changed `@` from the VM's A record to Railway's CNAME and added Railway's `_railway-verify` TXT record, both resolvers would return Railway's address. Within a few minutes Railway would issue a certificate for `brandondong.me`, and the check would return `HTTP 200 {"status":"ok"}`, the same as the Railway-provided URL already did.

## 2. Failed check and evidence

**Before the change (2026-10-08):** `https://brandondong.me` returned HTTP 200 from `20.80.7.163` (the VM), with the VM's Let's Encrypt certificate.

**Change (2026-10-12 21:48:42 UTC), made with the Cloudflare CLI:**
- `@` changed from `A 20.80.7.163` to `CNAME gvb8rrd4.up.railway.app`, DNS only
- added `TXT _railway-verify` = Railway's token
- `www` left on the VM

**First failed check (21:48:58 UTC), repeated every 20 s for 30 minutes with the same result:**

```text
$ curl -sv https://brandondong.me/healthz
*   Trying 69.46.46.57:443...
* schannel: SNI or certificate check failed: SEC_E_WRONG_PRINCIPAL (0x80090322) - The target principal name is incorrect.
```

Chrome showed "Not secure" for `brandondong.me`.

**Evidence collected 2026-10-12 22:36 UTC:**

```text
$ nslookup brandondong.me 1.1.1.1      ->  69.46.46.57
$ nslookup brandondong.me 8.8.8.8      ->  69.46.46.57
$ nslookup gvb8rrd4.up.railway.app 1.1.1.1  ->  69.46.46.57
$ nslookup -type=TXT _railway-verify.brandondong.me 1.1.1.1 / 8.8.8.8
      ->  "railway-verify=8340fab8…3031e"   (exact match with Railway's token on both)

$ openssl s_client -connect brandondong.me:443 -servername brandondong.me | openssl x509 -noout -subject -issuer -ext subjectAltName
subject=CN=*.up.railway.app
issuer=C=US, O=Let's Encrypt, CN=YE2
X509v3 Subject Alternative Name: DNS:*.up.railway.app, DNS:up.railway.app

$ curl -sk https://brandondong.me/healthz          # -k skips the certificate check, for diagnosis only
{"status":"error","code":404,"message":"Application not found",...}   HTTP 404 via 69.46.46.57

$ curl -s http://brandondong.me/                   ->  HTTP 301 -> https://brandondong.me/
$ curl -s https://career-platform-production-17c6.up.railway.app/healthz  ->  {"status":"ok"}  HTTP 200
```

**Railway dashboard (same time):** for `brandondong.me`, the CNAME showed a green check and the TXT showed a yellow warning: "Waiting for DNS update".

## 3. Diagnosis

- **DNS works.** Cloudflare holds the CNAME, and at the root it answers with Railway's address (CNAME flattening). Both public resolvers agree on `69.46.46.57`, the same address as Railway's target, and both return the exact TXT token. There are no mixed answers, so the request does reach Railway's edge.
- **TLS fails at the certificate name.** Railway's edge presents its generic `*.up.railway.app` certificate. The certificate itself is valid, but it doesn't list `brandondong.me`, so curl and Chrome reject the name. That's the failing step.
- **It's not the app.** The same service answers 200 on its Railway URL. But skipping the certificate check on my domain returns Railway's **404 "Application not found"**, not my app. So Railway's edge hasn't attached my hostname to the service yet.

**Conclusion:** Railway hasn't finished verifying that I own the domain (the TXT step), and that verification gates both the certificate and the routing for `brandondong.me`.

**Uncertain:** why Railway hasn't accepted a TXT record that public resolvers return correctly. I can't see Railway's verifier. My zone's negative-cache time is 30 minutes, so Railway may have cached "no record" from before I created it, but the check was still stuck after that window. Railway's help forum had several reports of this exact symptom in the same week, each fixed when Railway staff re-triggered verification.

## 4. Repair and repeated check

**Proposed repair:** my DNS records are correct, so changing them won't help. The repair is on Railway's side: ask Railway (Central Station) to re-trigger domain verification and certificate issuance. If the site has to be secure before Railway responds, the safe fallback is rolling `@` back to `A 20.80.7.163`, which brings back the VM and its valid certificate. The cost is that Railway can't verify while the domain points away.

**Repeated check (22:36 UTC, same command):** `curl https://brandondong.me/healthz` still fails with the wrong-name certificate.

**Repeated again (23:51 UTC, same checks):** still the same `*.up.railway.app` certificate, `curl` still fails, and `curl -k` still returns Railway's 404 "Application not found". **The failure remains, and I haven't verified a repair.**

**Compared with my first diagnosis:** at first I thought the certificate was just slow to issue. The dashboard's TXT warning, and then the `curl -k` 404, made me revise that: the domain isn't verified, so Railway neither issues the certificate nor routes the hostname. DNS was never the problem.

## 5. What I learned

**A check that separates DNS from TLS from the app:** `openssl s_client -servername <host>` shows exactly which certificate the server presents for that name. Combined with `curl -k`, it shows what's behind the TLS step. Here, DNS reached the right IP, the certificate was the platform's wildcard instead of mine, and `-k` showed the platform's 404 instead of my app. Comparing against the provider's own URL (which returned 200) ruled out the app and the database.
